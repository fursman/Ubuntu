# Single-GPU VFIO Passthrough + Looking Glass

Hardware-specific notes for the Razer Blade Pro 17 (RZ09-0368, Early 2021):
i7-10875H, RTX 3080 Mobile, 64 GB RAM, second 2 TB NVMe holding Windows.

Everything here is installed by `../gpu-passthrough.sh`. This document explains
*why* each piece exists, because most of it is non-obvious and was arrived at by
hitting a specific failure.

---

## The core problem

The laptop has one GPU worth passing through. There is no second discrete card
to keep the host running while the guest takes the first. The usual desktop
answer — bind the GPU to `vfio-pci` at boot and let the host live on a different
card — only works here because the CPU has an integrated GPU (CometLake-H UHD
Graphics) that Linux can fall back to.

That still leaves a conflict: you want NVIDIA on Linux for CUDA and a fast
desktop *most* of the time, and you want it inside Windows *some* of the time.
Rebinding a live GPU between `nvidia` and `vfio-pci` at runtime is famously
fragile — the NVIDIA driver does not reliably release the device, and a failed
rebind takes the desktop with it.

## The chosen answer: decide at boot

Rather than rebind, the machine has **two GRUB entries** and the decision is
made before any driver loads.

| Entry | GPU owner | Desktop runs on | CUDA | VM |
|---|---|---|---|---|
| `Ubuntu` (default) | `nvidia` | RTX 3080 | yes | no |
| `Ubuntu (GPU Passthrough)` | `vfio-pci` | Intel UHD | no | yes |

The second entry is generated by `/etc/grub.d/40_gpu-passthrough`. It is a
*script*, not a static `40_custom` block, so it re-resolves the newest kernel
and the `/boot` UUID on every `update-grub`. A hand-written static entry would
silently point at a deleted kernel after the next upgrade — this is the single
most important detail in the whole setup.

The only difference in its kernel command line is:

```
vfio-pci.ids=10de:249c,10de:228b
```

`10de:249c` is the GA104M GPU, `10de:228b` its HDMI audio function. Both must go
across: the guest's NVIDIA driver enumerates the audio function and misbehaves
if it is missing.

`intel_iommu=on` lives on the **normal** command line in `/etc/default/grub`,
not just the passthrough entry, because IOMMU groups must be available on every
boot for the tooling to introspect them.

### Backstop: module load order

`/etc/modprobe.d/vfio.conf`:

```
softdep nvidia        pre: vfio-pci
softdep nvidia_drm    pre: vfio-pci
softdep nvidia_modeset pre: vfio-pci
```

If anything pulls `nvidia` in early — an initramfs hook, a udev coldplug —
these force `vfio-pci` to be loaded first so it claims the device. Without this
the `vfio-pci.ids=` parameter can lose the race and you boot the passthrough
entry with the GPU still owned by NVIDIA.

### IOMMU group

```
Group 1:  00:01.0  PCI bridge (x16 root port)
          01:00.0  GA104M [10de:249c]
          01:00.1  GA104 HD Audio [10de:228b]
```

Clean — the group holds the GPU, its audio function, and the root port above
them. No ACS override patch is needed, which is fortunate: ACS override is a
non-upstream kernel patch and would break on every kernel update.

## Looking Glass: getting the picture back

With the GPU inside the guest, its output goes to a display the host cannot
see. Looking Glass solves this by having a Windows-side host application copy
each finished frame into a shared memory region, which a Linux-side client
reads and draws in a normal window.

### `kvmfr` instead of a shm file

The naive setup backs the shared region with a file in `/dev/shm`. This works
but every frame takes a trip through the page cache.

`kvmfr` is a small kernel module (built via DKMS from the Looking Glass source
tree) that exposes the region as a character device, `/dev/kvmfr0`. The client
`mmap`s it directly and can DMA out of it, which is why `client.ini` sets:

```ini
[app]
shmFile=/dev/kvmfr0
allowDMA=yes
```

Sizing, from `/etc/modprobe.d/kvmfr.conf`:

```
options kvmfr static_size_mb=128
```

The rule is `width × height × 4 bytes × 2 frames`, rounded up to a power of two.
3840×2160 needs 63 MiB → 64 MiB; 128 MiB leaves headroom for high-refresh
buffering.

`/etc/udev/rules.d/99-kvmfr.rules` gives the device to the desktop user, since
the client is not privileged:

```
SUBSYSTEM=="kvmfr", OWNER="user", GROUP="kvm", MODE="0660"
```

The QEMU side is wired up through `<qemu:commandline>` in the domain XML, using
an `ivshmem-plain` device backed by `memory-backend-file` pointing at
`/dev/kvmfr0` with `size=134217728` (128 MiB — must match `static_size_mb`).

Release the captured cursor with **Right-Ctrl**.

## Making the guest's NVIDIA driver cooperate

NVIDIA's driver historically refuses to initialise in a VM. Three separate
mitigations are stacked in the domain XML, each addressing a different check.

### 1. Hide the hypervisor

```xml
<kvm><hidden state='on'/></kvm>
<hyperv mode='custom'>
  <vendor_id state='on' value='GenuineIntel'/>
  ...
</hyperv>
<vmport state='off'/>
```

`<kvm><hidden/>` clears the `KVM` CPUID signature. The Hyper-V enlightenments
are kept (they are a large performance win for Windows) but the vendor ID is
spoofed so the driver does not see a recognisable hypervisor string.

### 2. Hand over a real vBIOS

```xml
<rom file='/usr/share/qemu/gpu.rom'/>
```

A laptop GPU has no VGA BIOS in a place OVMF can shadow. Without an explicit
ROM the guest gets a black screen and Code 43. The image is dumped from the
card itself — see `passthrough/assets/README.md`. It is a proprietary firmware
blob and is deliberately **not** committed to this public repo.

### 3. Fake a battery

This is the subtle one. The driver treats a *mobile* GPU differently, and part
of its sanity check is "am I in a laptop?" — answered by looking for an ACPI
battery. A VM has none, so a mobile GPU in a VM looks wrong and fails.

`passthrough/acpi/ssdt-battery.asl` is a minimal SSDT declaring one
`PNP0C0A` device reporting a permanently-full battery:

```asl
Device (BATT) {
    Name (_HID, EisaId ("PNP0C0A"))
    Name (_STA, 0x1F)
    Method (_BIF) { Return (Package (0x0D) { One, Ones, Ones, One, 0x2A30, ... }) }
    Method (_BST) { Return (Package (0x04) { Zero, Ones, Ones, 0x2A30 }) }
}
```

Injected via `-acpitable file=/usr/share/qemu/ssdt-battery.aml`.

The ASL **source** is kept in the repo, not just the compiled `.aml`, so the
table is auditable and can be rebuilt with `iasl`. `gpu-passthrough.sh`
recompiles it at install time and only falls back to the prebuilt blob if
`iasl` is unavailable.

### 4. SMBIOS that matches the hardware

```
-smbios type=1,manufacturer=Razer,product=Blade 17,...
-smbios type=17,manufacturer=Samsung,speed=3200,part=M471A2G43AB2-CWE
```

Consistent with a real Blade 17, so the guest's view of itself does not
contradict the mobile GPU it has been given.

## Performance tuning

### CPU pinning

The i7-10875H is 8 cores / 16 threads. The guest gets 8 vCPUs arranged as
**4 cores × 2 threads**, pinned so each guest core maps to a real physical core
and its sibling:

```xml
<vcpupin vcpu='0' cpuset='4'/>   <vcpupin vcpu='1' cpuset='12'/>   <!-- core 4 -->
<vcpupin vcpu='2' cpuset='5'/>   <vcpupin vcpu='3' cpuset='13'/>   <!-- core 5 -->
<vcpupin vcpu='4' cpuset='6'/>   <vcpupin vcpu='5' cpuset='14'/>   <!-- core 6 -->
<vcpupin vcpu='6' cpuset='7'/>   <vcpupin vcpu='7' cpuset='15'/>   <!-- core 7 -->
<emulatorpin cpuset='0-3,8-11'/>
```

Threads 0–3 and 8–11 are left to the host *and* carry QEMU's own emulator
threads, so guest vCPU threads never contend with the I/O thread that feeds
them. `<topology cores='4' threads='2'/>` tells Windows the truth about the
layout so its scheduler pairs threads correctly.

### Memory

```xml
<memoryBacking><hugepages/><nosharepages/><locked/></memoryBacking>
```

16 GiB from 8192 × 2 MiB hugepages, preallocated at boot by
`/etc/sysctl.d/99-hugepages.conf`. `<locked/>` prevents the host swapping guest
RAM — mandatory for VFIO anyway, since passed-through devices DMA to fixed
physical addresses. `<memballoon model='none'/>` because ballooning and
hugepages do not mix.

Hugepages must be reserved early; on a long-running host memory fragments and
the allocation silently comes up short. The script checks the actual count
after applying and warns if it did not get all 8192.

### Storage

```xml
<disk type='block'>
  <driver name='qemu' type='raw' cache='none' io='native' discard='unmap'/>
  <source dev='/dev/nvme0n1'/>
```

The guest gets the **whole physical NVMe**, not an image file — it is a real
Windows install that also boots on bare metal. `cache='none'` + `io='native'`
gives the guest direct O_DIRECT access with no host page-cache duplication, and
`discard='unmap'` lets Windows TRIM propagate to the SSD.

### Governor

`/etc/udev/rules.d/50-cpu-performance.rules` pins all cores to the
`performance` governor. With half the threads handed to the guest, the host
racing to idle causes audible stutter inside the VM.

## Convenience

### 8BitDo controller auto-attach

`99-8bitdo-passthrough.rules` matches the pad's USB IDs (including the
Nintendo-mode `057e:2009` identity it presents in one of its modes) and runs
`/usr/local/bin/8bitdo-passthrough`, which `virsh attach-device`s it to the
running guest.

It goes through libvirt rather than raw QEMU so AppArmor and cgroup device
permissions are set up correctly. It also detaches stale hostdev entries from
earlier enumerations — the pad re-enumerates when it changes modes and would
otherwise accumulate dead entries.

Exits silently if `win10-lg` is not running.

### USB wake

`90-disable-usb-wakeup.rules` disables PCI wakeup on the Intel xHCI controller.
This laptop otherwise wakes from suspend spontaneously.

## Day-to-day use

```bash
# check everything without changing anything
./gpu-passthrough.sh --check

# reboot, pick "Ubuntu (GPU Passthrough)" from GRUB, then:
virsh start win10-lg
looking-glass-client
```

To go back to CUDA and an NVIDIA-driven desktop, reboot and take the default
entry.

## Recovery notes

- The vBIOS lives at `~/.local/share/vfio-assets/gpu.rom` and in the pre-upgrade
  backup on the Recovery disk. It is **not** in git.
- `virsh dumpxml win10-lg > passthrough/vm/win10-lg.xml` re-captures the domain
  after any change made through virt-manager.
- If the passthrough entry disappears from GRUB, check that
  `/etc/grub.d/40_gpu-passthrough` is still executable — `update-grub` skips
  non-executable files silently.
